1. KV Cache Prefill → Load (prefix hit) + Store (new tokens)

Inference Behavior

A new request arrives. With prefix caching (RadixAttention), the scheduler checks how much of the prompt's KV already exists in the offload tier.

Two sub-cases:

1a. No prefix hit (cold prefill) — Pure Store
Model computes KV for ALL prompt tokens → sequential Store to certus.

1b. Prefix cache hit (warm prefill) — Load THEN Store
K prefix blocks Loaded from SSD/DRAM → GPU. Model computes only M new tokens → M blocks Stored.
With >60% prefix hit ratios in production, Loads dominate prefill IO.

Storage Operations

  • Load: K prefix blocks read (sequential, block 0..K) — if prefix was offloaded
  • Store: M new blocks written (sequential, block K..K+M) — only the unique tail
  • Semantics: Write-once, content-addressed (same prefix = same hash = skip Store)
  • Concurrency: Multiple requests prefilling simultaneously (continuous batching)

2. Cohort Sharing → N × Load of Same Blocks

Inference Behavior

Multiple requests share a common system prompt or document prefix. The first request computes and Stores the prefix. All subsequent requests Load it from storage.

Storage Operations

  • Store: First request in cohort Stores K prefix blocks (cold prefill)
  • Load: N-1 subsequent requests each Load the same K blocks (prefix cache hit)
  • Net: 1 Store + (N-1) × Load of same blocks — Load-dominated
  • Sharing ratio: 60–90% of tokens shared (system prompt + few-shot)

Key insight: Shared prefix blocks are hot — Loaded N times but Stored once. The DRAM tier should serve repeated Loads without hitting SSD.

3. Decode Phase → Load (cache miss) + Store (new block full)

Inference Behavior

After prefill, the model generates tokens one at a time. Each token needs ALL previous KV for attention. New KV accumulates until a full block (16 tokens) triggers a Store.

Storage Operations

OperationWhenDirectionLatency
Load (cache miss)Evicted block needed for attentionSSD→DRAM→GPUCritical path — blocks generation
Store (new block full)Every 16 generated tokensGPU→DRAM→SSDBackground (deferred)
  • Loads: Only on cache miss. Random across sessions. Latency-critical.
  • Stores: Fixed rate (1 per 16 tokens). Sequential per request. Background.
  • Under no memory pressure: zero storage IO — everything stays on GPU/DRAM.

Key insight: Decode Loads are on the critical path for TPOT (time per output token). When they happen, they directly impact generation latency.

4. Eviction Pressure → Store (flush) + Load (reload on reaccess)

Inference Behavior

GPU HBM and DRAM staging tiers are full. LRU eviction selects cold blocks to flush. When evicted blocks are needed again later, they must be reloaded.

Storage Operations

OperationWhenDirectionPattern
Store (eviction flush)DRAM tier exceeds watermarkDRAM→SSDScattered (LRU blocks are spatially random)
Load (reload on miss)Evicted block needed by decode/prefillSSD→DRAM→GPURandom (workload-dependent reaccess)

Key contention: Eviction Stores and prefix-cache Loads happen simultaneously — new requests need to Load prefixes while the tier is full and evicting. This is the bidirectional contention v3 measures.

5. Shared Prefix → Unique Suffix (The Compound Pattern)

Inference Behavior

N sessions share a common tool output, document, or system prompt, then each continues with unique conversation. First request Stores the prefix; subsequent requests Load it.

Storage Operations

Time →

Session 1: [STORE shared blocks 0..K] → [STORE unique blocks K+1..K+M₁]  (first in cohort)
Session 2: [LOAD shared blocks 0..K]  → [STORE unique blocks K+1..K+M₂]
Session 3: [LOAD shared blocks 0..K]  → [STORE unique blocks K+1..K+M₃]
...
Session N: [LOAD shared blocks 0..K]  → [STORE unique blocks K+1..K+M_N]

Net: 1 Store of K blocks + (N-1) × Load of K blocks + N × Store of M unique blocks.

6. Additional Patterns (Validated via Research)

6a. Chunked Prefill (Sarathi-Serve)

Long prompts split into fixed chunks (512–2048 tokens). Pattern: periodic medium write bursts interleaved with decode reads. Each chunk writes ~4 MB KV then yields to decode steps.

6b. Speculative Decoding / Tree Verification (SpecInfer)

Branching factor 3–5×. Most branches rejected → write amplification. Pattern: high write + high discard (rollback), tree-structured reads.

6c. Beam Search / Parallel Sampling

B beams share prefix, diverge at each step. Copy-on-write semantics: physical blocks shared via refcount. N×read of shared blocks per step, COW write only at divergence.

6d. Continuous Batching Steady-State

No global prefill/decode phases. KV blocks allocated/freed asynchronously. Arrival bursts (10–100× variation per BurstGPT) → variable memory pressure. Pattern: mixed async alloc/free.

6e. Multi-Turn Conversation Reuse

KV from prior turns persisted to storage. Pattern: large read burst at turn-start (reload prior conversation) → small appends. Growing read set over conversation lifetime.

6f. Disaggregated Prefill-Decode (DistServe, Splitwise, Mooncake)

Storage = communication channel between nodes. Pattern: one-shot bulk write (prefill node) → one-shot bulk read (decode node). Llama-70B at 4K tokens ≈ 2.5–5 GB per request. Latency-critical.

6g. Selective/Sparse KV Retrieval (InfiniGen)

Only 10–30% of KV entries are important per attention step. Pattern: sparse random reads, not bulk sequential scan. Fundamentally different from full-prefix read.

6h. LRU Eviction with Prefix Awareness (vLLM)

Freed blocks added in reverse order: unique-suffix evicted first, shared-prefix preserved longer. Cold reads disproportionately hit unique-suffix blocks.

9. Research Findings & Sources

Key Findings

  • No existing KV cache storage workload generator exists. certus-api-bench would be first.
  • FlexGen: LP-scheduled "zig-zag" bulk transfers. Throughput-oriented (offline), not latency.
  • Write amplification from speculative decoding: branching factor 3–5× writes.
  • Temporal profile: Prefill = burst (2.5 GB in 100–500ms). Decode = steady 20–50ms/token. Read-dominated ~400:1.
  • Sharing ratios: System prompts (200–2000 tokens) 100% shared. >50% prefix hit in production.
  • Selective retrieval: Only 10–30% of KV entries important per attention step.

Reality Check: Single Client vs Multi Client

In production with Certus, there is ONE gRPC client per vLLM worker process.

vLLM Engine (1 process, TP=1)
  └── CertusGrpcOffloadingSpec (singleton per worker process)
       └── 1 gRPC channel → 1 stub (process-level singleton)
            └── certus-server (Rust, SPDK)
TP SizeClients to ServerNotes
TP=11 clientSingle engine, most common
TP=22 clientsOne per GPU worker process
TP=88 clientsEach with own gRPC channel

Concurrency within that single client: ThreadPoolExecutor(max_workers=4) + pipelined async gRPC futures. cuMemcpyBatchAsync batches N block copies per driver call.

For bench: --clients 1 --pipeline-depth 4 = realistic single-engine. --clients 4+ = TP>1 or multi-tenant.

GPU Region Granularity: 64 KB per-layer vs 2 MB SSD

The mismatch is real and performance-critical.

Scatter/Gather Flow (vLLM 0.23+ per-layer → Certus)

STORE (GPU→Server): Connector sends N=32 IPC handles per block (each ~64 KB stride) Server copies 64KB × 32 → ONE contiguous 2 MB DRAM slot Background writer flushes 2 MB slot to SSD as one extent LOAD (Server→GPU): Server reads 2 MB from SSD → DRAM staging Single-region (N==1): 1 × cudaMemcpyAsync(2MB, H2D) ← OPTIMAL Multi-region (N>1): 32 × cudaMemcpyAsync(64KB, H2D) ← scatter cuMemcpyBatchAsync: 1 driver call for all 32 copies ← amortized

For bench design: certus-api-bench uses --block-size 4M with ONE IPC handle per block → models the N==1 cross-layer case. Real vLLM 0.23+ sends 32 × 64KB regions. cuMemcpyBatchAsync amortizes this to near-N==1 overhead. A future bench variant could model per-region scatter by issuing 32 × 64KB operations per logical block.
