1. KV Cache Prefill → Large Sequential Writes

Inference Behavior

A new request arrives. The model processes the prompt tokens in one forward pass, generating KV cache entries for all prompt tokens simultaneously.

Storage Pattern

  • Write size: 2–80 MB per offloaded block (model-dependent)
  • Access: Sequential within a request — blocks written in monotonically increasing index order
  • Concurrency: Multiple requests prefilling simultaneously (continuous batching)
  • Semantics: Write-once, content-addressed (dedup by hash)
  • Burstiness: Prefill generates all blocks at once → burst of writes, then silence

Concurrent prefills1–8Limited by GPU memory

2. Cohort Sharing → Multiple Readers on Same Extent Range

Inference Behavior

Multiple requests share a common system prompt or document prefix. The KV cache for this shared prefix is computed once and reused (prefix caching / RadixAttention).

Storage Pattern

  • Read size: Same block size as writes (2–80 MB per block)
  • Access: N sessions all read the same set of blocks (the shared prefix)
  • After shared prefix: each session diverges into unique blocks
  • Sharing ratio: In real deployments, 60–90% of tokens can be shared prefix

Key insight: Shared prefix blocks are hot — read N times but written once. Primary caching opportunity.

Read concurrencyUp to cohort_size × blocksAll members reading simultaneously
Divergence pointAfter shared_blocksFan-out pattern

3. Decode Phase → Small Random Reads + Small Appends

Inference Behavior

After prefill, the model generates tokens one at a time. Each new token requires reading all previous KV cache entries and appending one new KV entry.

Storage Pattern

  • Reads: If KV was evicted, reload full blocks on cache miss
  • Writes: Accumulated until a full block (16 tokens) triggers a write
  • Access: Random across active sessions (scheduler interleaves)
  • Latency-critical: Each decode step blocks on KV availability

Note: In well-provisioned systems, decode rarely hits storage. When it does, it's latency-critical.

4. Eviction Pressure → Working Set Exceeding Capacity

Inference Behavior

GPU HBM and DRAM staging tiers are full. LRU/ARC eviction selects cold blocks to push down the tier hierarchy (GPU → DRAM → SSD).

Storage Pattern

  • Writes: Burst of eviction writes (scattered — LRU blocks are spatially random)
  • Concurrent with: Hot-path reads (loading prefixes for new requests)
  • Contention: Eviction writes compete with prefill reads on same NVMe devices
ParameterTypical RangeNotes
Eviction batch size1–32 blocks per cycleWatermark-based triggering
Write patternRandom (scattered)Unlike sequential prefill writes
Capacity ratio1.2–5× over-subscriptionworking_set / cache_capacity
Eviction frequencyEvery 1–5ms under pressurePer scheduling step

5. Shared Prefix → Unique Suffix (The Compound Pattern)

Inference Behavior

N sessions share a common tool output, document, or system prompt, then each continues with unique conversation. The canonical pattern for multi-user chat, RAG, tool-use, batch processing.

Storage Pattern

Time →

Session 1: [READ shared blocks 0..K] → [WRITE unique blocks K+1..K+M₁]
Session 2: [READ shared blocks 0..K] → [WRITE unique blocks K+1..K+M₂]
Session 3: [READ shared blocks 0..K] → [WRITE unique blocks K+1..K+M₃]
...
Session N: [READ shared blocks 0..K] → [WRITE unique blocks K+1..K+M_N]

6. Additional Patterns (Validated via Research)

6a. Chunked Prefill (Sarathi-Serve)

Long prompts split into fixed chunks (512–2048 tokens). Pattern: periodic medium write bursts interleaved with decode reads. Each chunk writes ~4 MB KV then yields to decode steps.

6b. Speculative Decoding / Tree Verification (SpecInfer)

Branching factor 3–5×. Most branches rejected → write amplification. Pattern: high write + high discard (rollback), tree-structured reads.

6c. Beam Search / Parallel Sampling

B beams share prefix, diverge at each step. Copy-on-write semantics: physical blocks shared via refcount. N×read of shared blocks per step, COW write only at divergence.

6d. Continuous Batching Steady-State

No global prefill/decode phases. KV blocks allocated/freed asynchronously. Arrival bursts (10–100× variation per BurstGPT) → variable memory pressure. Pattern: mixed async alloc/free.

6e. Multi-Turn Conversation Reuse

KV from prior turns persisted to storage. Pattern: large read burst at turn-start (reload prior conversation) → small appends. Growing read set over conversation lifetime.

6f. Disaggregated Prefill-Decode (DistServe, Splitwise, Mooncake)

Storage = communication channel between nodes. Pattern: one-shot bulk write (prefill node) → one-shot bulk read (decode node). Llama-70B at 4K tokens ≈ 2.5–5 GB per request. Latency-critical.

6g. Selective/Sparse KV Retrieval (InfiniGen)

Only 10–30% of KV entries are important per attention step. Pattern: sparse random reads, not bulk sequential scan. Fundamentally different from full-prefix read.

6h. LRU Eviction with Prefix Awareness (vLLM)

Freed blocks added in reverse order: unique-suffix evicted first, shared-prefix preserved longer. Cold reads disproportionately hit unique-suffix blocks.

9. Research Findings & Sources

Key Findings

  • No existing KV cache storage workload generator exists. certus-api-bench would be first.
  • FlexGen: LP-scheduled "zig-zag" bulk transfers. Throughput-oriented (offline), not latency.
  • Write amplification from speculative decoding: branching factor 3–5× writes.
  • Temporal profile: Prefill = burst (2.5 GB in 100–500ms). Decode = steady 20–50ms/token. Read-dominated ~400:1.
  • Sharing ratios: System prompts (200–2000 tokens) 100% shared. >50% prefix hit in production.
  • Selective retrieval: Only 10–30% of KV entries important per attention step.
