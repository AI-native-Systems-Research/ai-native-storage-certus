## Root Causes of Flat Cold Scaling

### 1. Global dispatcher mutex serializes all clients — `service.rs:28`

```rust
pub struct DispatcherService {
    dispatcher: Arc<Mutex<Arc<dyn IDispatcher + Send + Sync>>>,
}
```

Every gRPC call (populate, lookup, check, remove) takes this mutex inside `spawn_blocking`. With 16 concurrent clients, only **one client's batch runs at a time** — the other 15 queue behind the lock. Per-drive thread parallelism in `batch_lookup` only ever occurs within a single client's request, never across clients simultaneously.

### 2. GPU PCIe H2D bandwidth is the actual ceiling

Within one `batch_lookup`, `thread::scope` does fan out per-drive (4 drives × 2 threads each for a 16-entry batch). But all those threads call `pipelined_ssd_to_gpu_zero_copy` → `dma_copy_to_device_async`, which sends data to the GPU through the **same PCIe H2D bus**. At 9.7 GB/s you're already at the PCIe H2D ceiling for the observed workload. More drives deliver NVMe data faster but can't push it through GPU PCIe any faster.

### 3. Zero-copy path is not actually pipelined — `pipeline.rs:307`

Despite its name, `pipelined_ssd_to_gpu_zero_copy` does:
```
Phase 1: all NVMe reads complete → memory-tier (pinned)
Phase 2: all CUDA H2D copies → GPU
```
There's no overlap between NVMe I/O and GPU DMA within a single object's promotion. The original `pipelined_ssd_to_gpu` (ring buffer path) had true overlap; the zero-copy path gave up pipelining in exchange for eliminating the intermediate memcpy.

### 4. `MAX_QUEUES_PER_DRIVE = 2` — `lib.rs:1026`

With 4 drives and 16 entries per batch, each drive gets 4 entries and `min(2, 4) = 2` threads, `queue_depth = 16/2 = 8`. That's enough NVMe depth, but it only fires up once the mutex is held — still serialized against other clients.

---

### Why the numbers are flat and not zero

Inside a single locked batch, 4 drives do fan out work in parallel threads. The 1-drive case uses 2 threads all hitting one drive; the 4-drive case uses 8 threads across 4 drives — the NVMe reads are 4× more parallel. But they all converge at the GPU PCIe write path immediately after, so the end-to-end latency per batch is GPU-PCIe-bound in both cases. The aggregate throughput ends up the same regardless of drive count.

---

### Fix priority

1. **Remove the global mutex** — use `RwLock<Arc<...>>` or eliminate it entirely (the dispatcher's internal state is already protected with `RwLock`/`Mutex` per-field). This alone would expose true multi-client concurrency and reveal whether NVMe scales.
2. **GPUDirect Storage** — direct NVMe→GPU DMA (bypassing CPU/DRAM) would eliminate the PCIe H2D bottleneck and reveal SSD scaling for real.
3. **Restore pipelining in zero-copy path** — interleave NVMe reads and GPU H2D copies to hide GPU latency behind I/O.

### Observations

**Hot lookup** is flat across all drive counts at ~24–25 GB/s, as expected — it reads from the 256 MiB DRAM memory tier which is independent of SSD count.

**Populate** is 2–2.3× faster than the serialized baseline (~11–12 GB/s vs 5.43 GB/s), reflecting the benefit of removing the global mutex so 16 clients can write to the memory tier truly concurrently. It doesn't scale cleanly with drive count because populate is bounded by the single background writer thread (write-through to SSD is serial) and GPU→DRAM DMA bandwidth, not drive count.

**Cold lookup** is 11–19% faster than the serialized baseline (10–11.5 GB/s vs 9.70 GB/s) but also doesn't scale with drive count. **What needed fixing along the way** to get here:
1. Global `Mutex` on the dispatcher — removed ✓
2. Zero-copy pipeline: all reads before any GPU copies — replaced with sliding window ✓
3. Eviction contention under concurrent promotes — `evict_lru()` as primary fast path ✓
4. CUDA IPC handle opened N times per batch entry (N = batch_size = 10) — cached once per unique handle ✓
5. VFIO not releasing between runs — cleaned up manually each sweep ✓
