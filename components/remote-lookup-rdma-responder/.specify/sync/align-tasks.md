**Current Code**: `ResponderEvent::Error` is never constructed anywhere in the
crate (`grep -rn "ResponderEvent::Error" src/` → no hits). The one candidate
non-fatal failure in production code — `RealCmSeam::drain_cm_events`'s

`rdma_reject` and silently drops the connection: no `Error` event is emitted to
`remote-lookup`, nothing is logged, and (per the task above) nothing is
counted.

**Required Change**: On the QP-creation-failure branch (and any other

the control channel via the existing `send_event` path (`src/lib.rs:130-132`),
in addition to the `rdma_reject`. This closes the same gap as the FR-016 task
above and should be implemented together with it since both consume the
QP-creation-failure signal.

**Files to Modify**: `src/rdma.rs` (`accept_child` / `drain_cm_events` failure
branch), `src/lib.rs` or `src/connection.rs` (whichever owns the path to
`send_event` from the accept-loop thread).

**Estimated Effort**: Small–Medium

### Acceptance Criteria

- [ ] Fatal safety-guarantee faults (§4, the asserted QP→ERROR transition) continue to fail-stop and are **not** rerouted through `ResponderEvent::Error` — only non-fatal accept-loop failures are.

## Task: Align 001-rdma-lookup-responder/FR-014 — route accept-loop diagnostics through `ILogger`

**Spec Requirement**: FR-014 ("Diagnostics MUST route through an optional
`ILogger` receptacle; a missing logger MUST NOT turn any operation into an
error.").

**Current Code**: Only two call sites exist: `initialize()` success and
`shutdown()` (`src/lib.rs:115-120,244,334` — `log_debug("rdma responder
initialized")` / `"...shut down"`). The accept-loop closure spawned in
`initialize_inner` (`src/lib.rs:312-324`) captures no reference to
`self.logger`, so no diagnostic from inside `run_accept_loop`,
`RealCmSeam::next_events`/`drain_cm_events`, or `accept_child`'s failure branch
can ever reach the logger. `src/rdma.rs` has zero `ILogger` references. The
"missing logger must not become an error" half is already satisfied
(`lifecycle_succeeds_with_no_logger_bound`); only the affirmative "route
diagnostics through it" half is under-implemented, and only for the
accept-loop's internal failure paths — this is Low-Medium severity (harmless
today, but no operator-visible signal from inside the loop).

**Required Change**: Give the accept-loop closure a handle to the logger
receptacle (e.g. a cloned `Arc<dyn ILogger>` / `Option<Arc<dyn ILogger>>`
captured at spawn time, mirroring how `self.logger` is already read in
`initialize()`/`shutdown()`), and call `log_debug`/`log_warn` (as appropriate)
from the same failure branches touched by the two tasks above — at minimum the
QP-creation-failure path — so accept-loop diagnostics are observable via
`ILogger` and not only via the (currently dead) telemetry counter / event.

**Files to Modify**: `src/lib.rs` (`initialize_inner`, closure capture),
`src/rdma.rs` (`RealCmSeam` failure branches, if the seam itself needs a
logger handle rather than the caller logging around it).

**Estimated Effort**: Small

### Acceptance Criteria
- [ ] The accept-loop closure has access to a logger handle when one is bound.
- [ ] The QP-creation-failure branch logs a diagnostic when a logger is bound.
- [ ] `lifecycle_succeeds_with_no_logger_bound` (or an equivalent test) still passes: a missing logger never turns the same failure into an error.

## Task: Align interfaces/`iremote_lookup_rdma_responder.rs` — stale `set_bind_ip`/`initialize` doc comment

**Spec Requirement**: FR-002a (explicit-IP-else-auto-detect precedence,
`spec.md` lines ~297-305), corroborated by `src/rdma.rs:184-189`
(`first_active_rdma_ipv4`) and the `initialize_without_bind_ip_defers_to_autodetect`

**Current Code**: `IRemoteLookupRdmaResponderAdmin::set_bind_ip`'s doc comment
in `components/interfaces/src/iremote_lookup_rdma_responder.rs:256-262` states
that the responder *"never auto-detects the address"* and that `initialize()`
*"fails with `Bind`"* if no IP was supplied. This is the **pre-clarification**
(pre-2026-07-10) behavior. It directly contradicts FR-002a and the shipped
code/tests, which both auto-detect the first active RDMA device's IPv4 when no
explicit IP is supplied. `contracts/responder-control-interface.md:9` names
this file as the interface "source of truth", so the stale comment is actively
misleading to any `remote-lookup`/mainline author who reads only the interface
docs rather than this component's spec.

**Required Change**: Update the doc comment on `set_bind_ip` (and any
paired comment on `initialize`) to describe the auto-detect fallback per
FR-002a: explicit IP via `set_bind_ip()` takes precedence; otherwise the
responder auto-detects the first RDMA device with an active port and binds
its IPv4; `Bind` is returned only if the effective IP (supplied or
auto-detected) is missing/unusable, including when auto-detection finds no
active device.

**Files to Modify**: `components/interfaces/src/iremote_lookup_rdma_responder.rs`
(lines ~256-262). **Not editable by this spec-sync pass** — it is a `.rs` file
outside `specs/**`/`.specify/sync/**`, and this pass is restricted to Markdown

**Estimated Effort**: Small (doc-only; still needs review since
`components/interfaces` is shared)
