## Task: Align 001-block-device-kernel/FR-021

**Severity**: major

**Spec Requirement**: FR-021 — "Component MUST provide feature-gated
telemetry (`--features telemetry`) that tracks total ops, min/max/mean
latency, total bytes, and mean throughput." Also SC-006 — "Feature-gated
telemetry produces accurate `TelemetrySnapshot` values when enabled."

**Current Code**: Every call site passes a hardcoded literal `0` for
`latency_ns` into `TelemetryStats::record_op()`
(`src/actor.rs:312,373,609,689,747`), so `min_latency_ns`, `max_latency_ns`,
and `mean_latency_ns` are always `0` regardless of actual IO latency.
`InflightOp.start_ns` (`src/actor.rs:100`) is populated via
`Instant::now().elapsed().as_nanos()` (`src/actor.rs:456,530`) — the elapsed
time since a *freshly constructed* `Instant`, i.e. always ~0ns — and is never
read back to compute a real start-to-completion duration. Only `total_ops`,
`total_bytes`, and `mean_throughput_mbps` are actually accurate; latency
statistics are non-functional and silently misleading (report 0 instead of
erroring or omitting the field).

**Required Change**: Capture a real monotonic start timestamp
(`Instant::now()`, stored — not `.elapsed()` on a new instant) at submission
time for each op (sync and async paths), and compute the true elapsed
duration at completion time (or immediately after `submit_and_wait` returns,
for the sync paths) before passing it into `record_op()`'s `latency_ns`
argument. Verify with a new unit/integration test that exercises
`record_op` under a known artificial delay and asserts `min/max/mean_latency_ns`
are non-zero and consistent with the delay.

**Files to Modify**:
- `components/block-device-kernel/src/actor.rs` (lines 100, 312, 373, 456,
  530, 609, 689, 747 and the `InflightOp` struct definition)
- `components/block-device-kernel/src/telemetry.rs` (if `record_op` signature
  or `TelemetryStats` internals need adjustment)
- New/updated test in `components/block-device-kernel/tests/integration.rs`
  or a `src/actor.rs` unit test covering telemetry latency accuracy

**Estimated Effort**: medium

### Acceptance Criteria
- [ ] `InflightOp` stores a real submission-time `Instant` (not
      `.elapsed()` of a fresh instant)
- [ ] All eight call sites listed above pass a real measured `latency_ns`
      into `record_op()`, not a hardcoded `0`
- [ ] Sync paths (`ReadSync`/`WriteSync`/`WriteZeros`) measure elapsed time
      around `submit_and_wait`
- [ ] Async paths (`ReadAsync`/`WriteAsync`, harvest/completion path) compute
      elapsed time from submission `Instant` to completion harvest

## Task: FlushSync command was unhandled — ✅ FIXED on branch (compile-unblocker)

**Severity**: High (crate did not compile)

**Discovered during this sweep**: `interfaces::Command` gained a `FlushSync
{ ns_id }` variant (handled by the sibling `block-device-spdk-nvme`), but the
kernel actor's `process_command` match never covered it — so
`cargo build -p block-device-kernel` failed with `E0004` (non-exhaustive
patterns) at HEAD. This went unnoticed because `block-device-kernel` is a
workspace member but **not** a `default-member`, so CI / `cargo test --all`
never builds it. (`block-device-filesys` had the identical breakage.)

**Fix (staged on branch)**: added a `Command::FlushSync { ns_id }` arm that
validates `ns_id == 1` and returns `Completion::FlushDone { handle, Ok(()) }`.
The device is opened `O_DIRECT|O_DSYNC`, so every write is already forced to
non-volatile media on completion — there is no volatile write cache to drain,
making an explicit flush a correct validated no-op. Backfilled as spec FR-014
context is unaffected; the new command is documented indirectly via the
`IBlockDevice` contract. **Review note**: this is a code change beyond the
planned telemetry fix, made to keep the branch buildable; confirm the no-op
semantics are the desired `FlushSync` contract for a kernel block device.
