5Stale handle never crashestouch, batch_touch, remove, clear_poolTouching a handle whose entry has already been removed, or already evicted, quietly succeeds and changes nothing: it does not crash, does not resurrect the entry, and does not disturb any other entry's position.Recording an access must never crash the process, whatever handle it is given. This obligation is expected to be refuted: the implementation reads the entry slot named by the handle without first checking that such a slot exists, so a handle whose slot number is at or beyond the number of slots the pool has ever allocated causes an out-of-bounds crash rather than the error the interface provides for exactly this case. Any handle issued before its pool was emptied has this shape. Stopping the tracking of an entry must never crash the process, whatever handle it is given. This obligation is expected to be refuted for the same reason as for recording an access: the slot named by the handle is read without any check that the slot exists, so a handle whose slot number is beyond the slots the pool has allocated causes an out-of-bounds crash instead of an error return. Emptying a pool must not leave the component in a state where a previously issued handle can crash it or corrupt it. This obligation is expected to be refuted: emptying a pool discards all its internal slots, so every handle the pool ever handed out now names a slot that no longer exists, and using any such handle to record an access or to stop tracking crashes the process with an out-of-bounds access. Worse, once new keys have been registered into the emptied pool, an old handle can instead name a live slot belonging to an unrelated key and quietly corrupt that key's position or remove it. No mechanism in the code marks old handles as expired.spec FR-012
