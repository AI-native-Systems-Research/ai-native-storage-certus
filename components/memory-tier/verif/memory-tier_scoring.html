How to read this page

The result above is at the level of individual properties. A property is one precise, checkable claim about how the component behaves (for example: every emitted log line ends with a single newline). This component has 161 such verifiable properties, and 137 of them carry a machine-checked proof from Creusot and/or Kani; 0 are soundly delegated to a named external tool, and 24 are left open — of which 13 are REFUTED: verification proved the implementation VIOLATES them, so they are defects to fix rather than unfinished work.

“Proved” means a tool proved the property itself. Each tool's scorer re-runs that tool's own artifact from source and checks it passes — Creusot: cargo creusot reports every goal Proved; Kani: cargo kani reports VERIFICATION SUCCESSFUL with the anti-vacuity __mutant twin going RED.

The two tools are complementary, so their individual counts differ and neither alone covers everything. Where one tool cannot even state a property (e.g. Creusot's logic model treats string contents as opaque), the other tool proves it — that is a sound hand-off, not a gap. The per-method tables further down group properties by the method they constrain; there B is simply the number of properties in that group (the “bundle size”), and proved / B is how many of them that one tool proves by itself.
