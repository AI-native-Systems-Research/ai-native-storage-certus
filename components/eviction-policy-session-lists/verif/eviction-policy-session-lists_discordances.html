2spec and code differtouchReporting an access with a handle that was never issued, or that names a block that has already been evicted or removed, must report an error to the caller instead of quietly doing nothing or acting on some other block, and must change nothing.The specification requires an error for any handle naming a block that has already been evicted or removed. The code only checks that the storage position named by the handle is beyond the end of the domain's storage or currently unoccupied (src/session_list.rs:80-82, 123-126). 10spec and code differget_eviction_candidates, identify_next_to_evictThe candidates are listed in the order the policy would actually evict them, oldest access first, so that the list read from front to back is the sequence of blocks successive victim requests would return.The specification promises the candidate list is in true eviction order. The code returns the currently eligible end-of-chain blocks sorted by recency, oldest first (src/session_list.rs:196-202), which guarantees only the FIRST entry: evicting that block promotes its parent into the eligible set at the parent's own, possibly much older, recency, so the block actually evicted second may be a block that was not in the list at all, or one further down it. The code extraction states this explicitly as a separate obligation. The specification's own first-entry claim is met; its whole-list ordering claim is not. 14spec and code differtrack, touch, batch_touch, clear_poolEvery time a block is registered or an access to it is reported, it is stamped with a recency value strictly later than every recency value handed out before it in that eviction domain, so recency only ever moves forward and older accesses can never appear newer than later ones.The specification promises that recency values strictly advance for the whole life of a domain. The code maintains only the weaker property that the domain's recency counter is at least as large as the recency of every block it currently tracks, and it resets that counter to zero when the domain is cleared (src/session_list.rs:226), so values handed out after a clear repeat values handed out before it. This is unobservable while it lasts, because clearing discards every block, so no two blocks ever share a recency value and the eviction order is never wrong - but the specification's monotonicity claim is literally false across a clear, and it becomes observable if a pre-clear handle is reused (see EPSL-CLEAR-INVALIDATES-EXISTING-HANDLES).
