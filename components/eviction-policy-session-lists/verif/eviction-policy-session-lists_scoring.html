How to read this page

EPSL-TRACK-UNKNOWN-DOMAIN-IS-AN-ERRORtrackRegistering a block into an eviction domain that does not exist reports an error to the caller, naming the offending domain identifier, instead of appearing to succeed, and leaves the tracking state of every existing domain exactly as it was.★

EPSL-TRACK-FRESH-KEY-BECOMES-THE-SESSION-LEAFtrack, len, get_eviction_candidatesRegistering a key the domain does not yet hold adds exactly one new block. EPSL-TRACK-DEMOTES-THE-PREVIOUS-LEAFtrack, get_eviction_candidates, identify_next_to_evictThe block that was previously the end of a session's chain stops being an eviction candidate the moment a new block is attached beneath it, because it now has a child that is still tracked. It is removed from the candidate set in the same operation that adds the new block.★
EPSL-TRACK-NEVER-REPORTS-INVALID-HANDLEtrackRegistering a block has exactly one way to fail, namely naming an eviction domain that does not exist. EPSL-TRACK-KEYS-ARE-SCOPED-TO-ONE-POOLtrack, len, get_eviction_candidatesThe record of which cache keys are already tracked is kept separately for each eviction domain, so the same key may be tracked independently in two different domains, and each domain then holds its own block for that key with its own session, its own place in a chain and its own recency.★

EPSL-BATCH-TOUCH-MATCHES-ONE-AT-A-TIMEbatch_touch, touchWhen a group recency refresh succeeds, it leaves the policy in exactly the condition that reporting those same accesses one at a time, in the order they appear in the group, would have produced. EPSL-BATCH-TOUCH-REJECTS-UNKNOWN-POOLbatch_touchIf any handle in the group names an eviction domain that does not exist, the whole call fails with an invalid-domain error naming that identifier. EPSL-BATCH-TOUCH-EMPTY-SUCCEEDS-WITHOUT-VALIDATIONbatch_touchReporting an empty group of accesses reports success, changes nothing at all, and does not even take a lock or check that any eviction domain exists.★
EPSL-BATCH-TOUCH-SPANS-POOLS-ONE-LOCK-AT-A-TIMEbatch_touchWhile refreshing a group of blocks that spans several eviction domains, the component always releases exclusive access to the domain it currently holds before taking exclusive access to the next one, so it never holds exclusive access to two domains at the same time.★
EPSL-BATCH-TOUCH-RELOCKS-WHEN-THE-POOL-CHANGESbatch_touchA group of handles may mix blocks from different eviction domains, and each block is refreshed in its own domain. EPSL-REMOVE-STOPS-TRACKING-THE-BLOCKremove, len, track, identify_next_to_evict, get_eviction_candidatesWhen the caller asks the policy to stop tracking a block, that block is no longer tracked afterwards: the reported size of its domain drops by exactly one, the block is never again offered as an eviction candidate or chosen as a victim, its cache key stops being tracked so the same key can later be registered again as a brand-new block, and its storage position is released for reuse.★
EPSL-REMOVE-RELINKS-THE-CHAINremove, identify_next_to_evictWhen the block being removed sits in the middle of a session's chain, the policy joins the two ends back together: the removed block's child is given the removed block's parent as its new parent, and that parent is given the child as its new child, so the session is still one unbroken chain with no gap and no dangling block.★
EPSL-REMOVE-LAST-BLOCK-EMPTIES-THE-SESSIONremove, identify_next_to_evict, get_eviction_candidatesWhen the block removed was the only block its session still held, that session is left with no blocks at all: the policy forgets the session entirely, it contributes no eviction candidate, and it starts fresh if a block is later registered for it again.★
EPSL-REMOVE-DISTURBS-ONLY-THE-CHAIN-NEIGHBOURSremove, identify_next_to_evictRemoving a block changes only that block's own record and the parent and child links of its immediate parent and child. No block's recency changes, no other block stops being tracked, and no block of any other session changes its parent, its child, its recency or its eligibility for eviction.★
EPSL-INV-PARENT-BECOMES-ELIGIBLE-WHEN-ITS-CHILD-GOESremove, identify_next_to_evict, get_eviction_candidatesAs soon as a block's only child stops being tracked, whether that child was evicted or explicitly removed, the block itself becomes the end of its session's chain and is therefore eligible for a later eviction. This is how a session's chain is consumed from the end back towards its start.★
EPSL-REMOVE-REJECTS-UNKNOWN-POOLremoveAsking to stop tracking a block through a handle that names an eviction domain that was never created fails with an invalid-domain error reporting that identifier, and nothing anywhere changes.★
EPSL-REMOVE-OF-AN-INTERIOR-BLOCK-KEEPS-THE-CANDIDATESremove, get_eviction_candidatesRemoving a block that still has a tracked child, including the block at the start of a chain, does not change which blocks are eviction candidates and does not change which block is the end of that session's chain.★
EPSL-REMOVE-DOES-NOT-REFRESH-RECENCYremove, identify_next_to_evictRemoving a block does not count as an access to anything: the domain's recency counter does not advance and no surviving block's recency changes, so the eviction order among the remaining candidates is exactly as it was apart from the removed block's disappearance.★
EPSL-PROMOTED-PARENT-KEEPS-ITS-OLD-STAMPremove, identify_next_to_evict, touch, batch_touchWhen a block becomes eligible for eviction because its child stopped being tracked, it enters the eviction order at the recency it already had, not as a freshly accessed block. A long-untouched parent therefore becomes the next victim immediately on promotion rather than going to the back of the queue.★
EPSL-TRACKED-SIZE-NEVER-UNDERFLOWSremove, identify_next_to_evictThe stored count of tracked blocks is decreased with no guard against dropping below zero, so the implementation relies on that decrease only ever happening for a block that really was being tracked. Every path that decreases it is reached only after the block has been confirmed to occupy its storage position.★
EPSL-EVICT-PICKS-OLDEST-ELIGIBLE-LEAFidentify_next_to_evictWhen asked for a victim, the policy returns the eligible block - a block with no still-tracked child - whose recency is the oldest among all such blocks anywhere in that eviction domain, comparing across every session in the domain at once. No eligible block with an older recency is ever passed over.★
EPSL-EVICT-STOPS-TRACKING-THE-VICTIMidentify_next_to_evict, len, track, get_eviction_candidatesThe block returned as the victim stops being tracked as part of the same operation, with exactly the same effect as an explicit request to stop tracking it: the domain's reported size drops by one, its cache key is no longer tracked, its session's chain is rejoined and its parent promoted, and the same block is never returned again by a later victim request or listed as a candidate.★
EPSL-EVICT-EMPTY-DOMAIN-REPORTS-NOTHINGidentify_next_to_evictWhen an eviction domain currently tracks no blocks at all, a request for a victim reports that there is nothing to evict rather than returning some block or failing, and it leaves the domain untouched.★
EPSL-EVICT-DOES-NOT-REFRESH-THE-VICTIMidentify_next_to_evictChoosing a block for eviction does not count as an access to it or to any surviving block: the domain's recency counter does not advance and no recency changes, so the selection can never make the block it just selected look recently used, and repeated victim requests walk steadily through the candidates from oldest to newest.★
EPSL-READONLY-QUERIES-DEGRADE-SAFELY-ON-UNKNOWN-DOMAINidentify_next_to_evict, get_eviction_candidates, len, clear_poolThe four operations that have no way to report an error - asking for a victim, asking for candidates, asking for a size, and clearing - behave harmlessly when asked about an eviction domain that does not exist: the victim request reports that there is nothing to evict, and nothing anywhere in the component changes. A consequence is that the caller cannot tell an unknown domain apart from one that is simply empty.★
EPSL-INV-A-BLOCK-WITH-A-DESCENDANT-IS-NEVER-EVICTEDidentify_next_to_evict, get_eviction_candidatesThe policy never selects as a victim, and never offers as a candidate, a block that still has a tracked block descended from it, however long ago that block was last accessed. Blocks at the start and in the middle of a chain are therefore protected until everything below them has gone. This is the whole point of the policy.★
EPSL-INV-VICTIM-CHOICE-IS-REPEATABLEidentify_next_to_evict, get_eviction_candidatesVictim selection depends only on the tracking state and never on anything incidental, and there is never any ambiguity about which block is chosen: because every access is stamped with its own recency value and no two tracked blocks in a domain share one, the eligible blocks have a strict oldest-to-newest order with a unique oldest. Two domains in identical states always name the same victim and produce the same candidate list.★
EPSL-CANDIDATES-NEVER-MORE-THAN-ASKEDget_eviction_candidatesWhen the caller asks for up to a given number of eviction candidates, the policy returns no more than that many and no more than the number of eligible blocks it is actually tracking, returning exactly as many as are available when fewer exist. Asking for zero candidates returns an empty list.★
EPSL-CANDIDATES-ARE-DISTINCTget_eviction_candidatesThe returned candidate list never names the same cache block twice; each entry is a different tracked block. Moreover no two entries ever belong to the same session, because a session has exactly one block with no tracked child, so the number of candidates available is the number of sessions currently holding blocks.★
EPSL-CANDIDATES-CHANGE-NOTHINGget_eviction_candidatesAsking for eviction candidates is a pure enquiry: none of the listed blocks is removed from tracking, the reported size of the domain is unchanged, no recency changes, the recency counter does not advance, and no parent or child link is altered. Asking twice in a row returns the same list.★
EPSL-CANDIDATES-ARE-LEAVES-OLDEST-FIRSTget_eviction_candidatesThe candidate list contains only blocks that have no tracked child, and they are listed least recently accessed first.★
EPSL-CANDIDATES-FIRST-IS-THE-NEXT-VICTIMget_eviction_candidates, identify_next_to_evictWhen at least one candidate exists, the first entry of the candidate list is exactly the block that the next victim request would choose, because both operations read the same oldest-first ordering of eligible blocks and take its first element.★
EPSL-CANDIDATES-UNKNOWN-POOL-RETURNS-EMPTYget_eviction_candidatesAsking an eviction domain identifier that was never created for eviction candidates returns an empty list rather than reporting an error, so the caller cannot tell an unknown domain apart from one that currently has no candidates.★
EPSL-LEN-REPORTS-TRACKED-COUNTlenThe reported size of an eviction domain is exactly the number of cache blocks the policy is currently tracking in it, counting blocks in every session and at every position in a chain, not only the ones eligible for eviction. It goes up by one for each newly registered block and down by one for each block removed or evicted.★
EPSL-LEN-CHANGES-NOTHINGlenAsking for the size of an eviction domain is a pure enquiry: it removes nothing, adds nothing, refreshes no block's recency, does not advance the recency counter, and changes no parent or child link.★
EPSL-LEN-UNKNOWN-POOL-RETURNS-ZEROlenAsking an eviction domain identifier that was never created for its size reports zero rather than an error, so a caller that mistypes an identifier sees what looks like an empty domain instead of being told the domain does not exist.★
EPSL-CLEAR-RETURNS-DOMAIN-TO-EMPTYclear_pool, len, identify_next_to_evict, get_eviction_candidatesClearing an eviction domain discards every block it was tracking, every session it knew about and every eviction candidate: afterwards its reported size is zero, a victim request reports nothing to evict, and a candidate request returns an empty list. The implementation also resets the domain's recency counter back to its starting value and discards its whole storage area.★
EPSL-CLEAR-LEAVES-DOMAIN-USABLEclear_pool, trackA cleared eviction domain is empty but still usable and keeps its identifier: registering a block into it afterwards succeeds, and that block starts a fresh chain for its session, with no parent, as if the session had never held any blocks.★
EPSL-CLEAR-POOL-UNKNOWN-POOL-IS-A-SILENT-NO-OPclear_poolClearing an eviction domain identifier that was never created does nothing at all and reports nothing at all. The operation returns no result, so the caller has no way to learn that the domain it named does not exist.★
EPSL-CLEAR-POOL-LEAVES-OTHER-POOLS-ALONEclear_poolClearing one eviction domain has no effect on any other domain: their blocks, chains, recency values, recency counters and reported sizes are all unchanged, and their identifiers stay valid.★
EPSL-INV-AT-MOST-ONE-CHILDtrack, remove, identify_next_to_evict, clear_poolA session's lineage is always a single straight chain and never a branching tree: at every moment no tracked block has more than one tracked child. This holds however long the chain is and whatever sequence of registrations, accesses, evictions and removals has been performed, because a new block is only ever attached beneath the session's current end-of-chain block, which by definition has no child.★
EPSL-INV-EXACTLY-ONE-LEAF-PER-SESSIONtrack, remove, identify_next_to_evict, clear_pool, get_eviction_candidatesEvery session that currently holds at least one block has exactly one end-of-chain block, that is one block with no tracked child, and that is the only block of that session eligible for eviction. Consequently the number of eviction candidates always equals the number of sessions currently holding at least one block, and a session holding no blocks contributes no candidate.★
EPSL-INV-NO-CYCLES-IN-LINEAGEtrack, remove, identify_next_to_evict, clear_poolFollowing the parent links upwards from any tracked block always reaches the start of its session's chain after a finite number of steps, never more steps than the number of blocks the domain holds. No block is ever its own ancestor, so the lineage can always be walked to the top without looping forever.★
EPSL-INV-NO-ORPHANED-BLOCKStrack, touch, batch_touch, remove, identify_next_to_evict, clear_poolWhenever a tracked block records another block as its parent, that parent is itself still tracked and records the first block as its child, and whenever it records a child, that child is still tracked and records it back as its parent. The two directions of every link always agree, so no tracked block is ever left referring to a block that has gone.★
EPSL-INV-ELIGIBLE-SET-IS-EXACTLY-THE-CHILDLESStrack, touch, batch_touch, remove, identify_next_to_evict, get_eviction_candidates, clear_poolThe set of blocks the policy considers for eviction is at every moment exactly the set of tracked blocks that have no tracked child: never a block that still has one, and never missing a block that has none. Each such block is listed once, recorded with its current recency, so the stored candidate set never disagrees with the chains themselves.★
EPSL-INV-SESSION-POINTS-AT-ITS-OWN-END-OF-CHAINtrack, remove, identify_next_to_evict, clear_poolFor every session the policy knows about, the block it remembers as that session's end of chain is still tracked, genuinely belongs to that session, and has no tracked child.★
EPSL-INV-ONE-TRACKED-BLOCK-PER-CACHE-KEYtrack, remove, identify_next_to_evict, clear_poolWithin one eviction domain no two tracked blocks ever carry the same cache key: the lookup table from key to block holds exactly one entry for every tracked block and nothing else, each entry points at a block that is still tracked and really holds that key, and every tracked block's key is in the table. This is what makes re-registering an existing key an access rather than a second registration.★
EPSL-INV-SIZE-ACCOUNTING-IS-EXACTlen, track, touch, batch_touch, remove, identify_next_to_evict, get_eviction_candidates, clear_poolThe size a domain reports always matches the blocks it really holds. It goes up by exactly one for each newly registered block, stays the same when an existing key is re-registered and when accesses are reported or enquiries made, and goes down by exactly one for each block removed or evicted. Equivalently it always equals the number of occupied storage positions, which is the total number of positions minus the number on the spare list, so the counter can never drift away from the real contents.★
EPSL-INV-LINEAGE-NEVER-CROSSES-SESSIONStrack, remove, identify_next_to_evict, clear_poolBlocks of different sessions are never linked to one another: a block's parent and its child always belong to the same session as the block itself, so every block in one chain names the same session and one session's blocks never appear anywhere in another session's chain. Rejoining a chain after a removal therefore never mixes sessions.★
EPSL-INV-DOMAINS-ARE-INDEPENDENTcreate_pool, track, touch, batch_touch, remove, identify_next_to_evict, get_eviction_candidates, len, clear_poolEvery operation affects at most the one eviction domain it names, and anything done to one domain leaves every other domain completely unchanged: no block, session, chain, recency value, recency counter or reported size in any other domain is ever altered, a victim is only ever chosen from the blocks of the domain asked about, and a reported size counts only that domain's blocks. Cache keys, session identifiers and handles are meaningful only within the domain they were used in.★
EPSL-HANDLE-VALIDATION-IS-OCCUPANCY-ONLYtouch, batch_touch, removeThe only checks made on a handle are that the eviction domain it names exists and that the storage position it names is currently occupied by some tracked block. Nothing ties a handle to the particular cache key, session or registration it was issued for.★
EPSL-INV-ACTIVE-STAMPS-ARE-DISTINCTtrack, touch, batch_touch, clear_poolNo two blocks tracked in the same eviction domain ever share a recency value, because every value handed out is larger than all the ones handed out before it in that domain and each block holds only the most recent value it was given.★
EPSL-INV-FREE-LIST-IS-EXACTLY-THE-EMPTY-SLOTStrack, remove, identify_next_to_evict, clear_poolThe list of spare storage positions contains every empty position exactly once and no occupied position. If a position appeared on that list twice, the next two blocks registered would be placed in the same position and one would silently overwrite the other.★

EPSL-INV-POOL-IDS-STAY-VALID-FOREVERcreate_pool, track, touch, batch_touch, remove, identify_next_to_evict, get_eviction_candidates, len, clear_poolOnce an eviction domain identifier has been handed out it stays valid for the rest of the component's life and always refers to the same domain. EPSL-INV-ARENA-ONLY-GROWS-EXCEPT-ON-CLEARtrack, touch, batch_touch, remove, identify_next_to_evict, clear_poolAn eviction domain's storage area only ever gets bigger, one position at a time, with the single exception of clearing the domain, which empties it completely. The counter is increased with no overflow guard, so reaching that limit would either abort the process or wrap round and corrupt the eviction order.★
EPSL-LOCKS-ASSUMED-NEVER-POISONEDcreate_pool, track, touch, batch_touch, remove, identify_next_to_evict, get_eviction_candidates, len, clear_poolEvery operation assumes no earlier operation crashed while holding one of the component's internal locks. The code takes each lock and assumes success unconditionally, so if such a crash ever happened every later operation on the component would itself abort.★

What these times include. Each figure is the sum of the first proof attempt per property, as measured by the scorer around one whole toolchain invocation (/usr/bin/time -v cargo kani --harness <h> or cargo creusot <module>). So it is build + proof, not solver time: a sub-second proof still shows seconds because compilation is counted with it, and Kani re-invokes the toolchain per harness while Creusot's runs are largely incremental — which is most of why Kani's per-property figures sit well above Creusot's. A figure at or near the cap (--cap-seconds, escalating once to --cap-max) is a timeout, not solving.
What they exclude. The scorer also runs an anti-vacuity __mutant twin for each proved property and the full lever battery for each tool-boundary; those invocations are not counted here, so one property can cost 2–5 runs while only the first is timed. Total machine cost per tool is the stage wall-clock in verif/.run/<stage>.done, which is larger than the sum above. Peak RSS is the largest single timed run, not a total. Agent time to author the proofs is not measured anywhere on this page.
