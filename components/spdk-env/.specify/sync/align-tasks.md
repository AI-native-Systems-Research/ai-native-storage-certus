## Task 1: NVMe-only device enumeration vs. "all VFIO devices" spec claim

- **Severity**: medium
- **Type**: ALIGN (spec-vs-code gap; code change or spec re-scope required)
- **Spec refs**: `specs/002-spdk-env-vfio-init/spec.md` — SC-001, User Story 1
  narrative ("probes for all SPDK-supported device types (NVMe, virtio-blk,
  etc.)"), Clarifications session answer ("All SPDK-supported device types
  bound to VFIO (NVMe, virtio-blk, etc.)"), FR-006 (narrows scope to NVMe-only)
- **Code**: `components/spdk-env/src/env.rs:164-181` (`enumerate_devices()`
  only calls `spdk_pci_enumerate()` against the driver returned by
  `spdk_pci_get_driver("nvme")`)
- **Description**: SC-001, the User Story 1 narrative, and the Clarifications
  answer all promise discovery of "all VFIO-bound devices" / "all
  SPDK-supported device types (NVMe, virtio-blk, etc.)". FR-006 already
  narrows this to NVMe-only, and the code implements FR-006's narrower scope,
  not the broader claim in SC-001/User Story 1/Clarifications. This is a real
  functional gap (virtio-blk and other SPDK-supported VFIO device types are
  never enumerated), not just a documentation inconsistency — resolving it
  requires either (a) extending `enumerate_devices()` to also enumerate other
  SPDK PCI driver types (virtio-blk, etc.), or (b) a deliberate decision to
  keep NVMe-only scope and reword SC-001/User Story 1/Clarifications to match
  FR-006 (this was NOT done in this pass, since it changes what capability is
  promised, which is beyond a text-only backfill).
- **Recommended next step**: Product/engineering decision on whether
  multi-device-type enumeration is actually needed. If yes: implement and
  file as a code task. If no: a follow-up spec-sync BACKFILL pass should
  narrow SC-001/User Story 1/Clarifications to NVMe-only to match FR-006 and
  the code.

## Task 3: Partial-initialization cleanup path doesn't call `spdk_env_fini()`

- **Severity**: medium
- **Type**: DEFECT / ALIGN (code gap, latent — currently unreachable)
- **Spec ref**: `specs/002-spdk-env-vfio-init/spec.md` Edge Cases — "What
  happens when the SPDK/DPDK initialization fails mid-way (partial
  initialization cleanup)? — The component cleans up any partially
  initialized state and returns an error from `init()`."
- **Code**: `components/spdk-env/src/env.rs:17-34` (`do_init`), `:37-70`
  (`do_init_inner`), `:115-185` (`enumerate_devices` — always returns
  `Ok(..)`, never constructs `SpdkEnvError::DeviceProbeFailed`)
- **Description**: `do_init()`'s error path only clears the
  `SPDK_ENV_ACTIVE` singleton flag; it never calls `spdk_env_fini()` to
  unwind a successful `init_spdk_env()` if a later step (currently only
  `enumerate_devices()`) were to fail. This is masked today because
  `enumerate_devices()` is written to always return `Ok(..)` — the
  `DeviceProbeFailed` error variant exists in `interfaces` but is never
  constructed in `spdk-env`. If enumeration is ever made fallible (e.g. as
  part of Task 1's virtio-blk extension, or FR-015's skip-and-warn logic),
  this becomes a real SPDK/DPDK resource leak on the error path. Requires a
  source change (add an `spdk_env_fini()` call to the `do_init_inner` error
  path after `init_spdk_env()` succeeds), which is out of scope for this
  Markdown-only sync-apply pass.
