How to read this page

The result above is at the level of individual properties. A property is one precise, checkable claim about how the component behaves (for example: every emitted log line ends with a single newline). This component has 80 such verifiable properties, and 80 of them carry a machine-checked proof from Creusot and/or Kani; 0 are soundly delegated to a named external tool, and 0 are left open.

“Proved” means a tool proved the property itself. Each tool's scorer re-runs that tool's own artifact from source and checks it passes — Creusot: cargo creusot reports every goal Proved; Kani: cargo kani reports VERIFICATION SUCCESSFUL with the anti-vacuity __mutant twin going RED.

The two tools are complementary, so their individual counts differ and neither alone covers everything. Where one tool cannot even state a property (e.g. Creusot's logic model treats string contents as opaque), the other tool proves it — that is a sound hand-off, not a gap. The per-method tables further down group properties by the method they constrain; there B is simply the number of properties in that group (the “bundle size”), and proved / B is how many of them that one tool proves by itself.

DPM-FORMAT-POST-REST-OF-DISKformat, initialize_or_formatIf one of the requested partitions was given a size of zero, that partition ends up covering exactly the drive space that is still free after every explicitly sized partition has been placed, so no usable space is left stranded.✓·
DPM-FORMAT-POST-MBRformat, initialize_or_formatWhen formatting succeeds, the very first sector of the drive holds a decoy legacy partition record, marked as non-bootable, describing a single region of type 0xEE that starts at sector 1 and spans the rest of the drive capped at the largest value that fits in its four-byte length field, which tells older tools that the drive is managed by the modern partitioning scheme and must not be touched.✓·
DPM-FORMAT-POST-HEADER-PAIRformat, initialize_or_formatWhen formatting succeeds, the main partition-table header is written to the second sector of the drive and a second copy of it is written to the very last sector, and each header records the sector it lives in and points at the other one, so the table can still be recovered if the copy at the front of the drive is damaged.✓·
DPM-FORMAT-POST-ENTRY-ARRAYformat, initialize_or_formatWhen formatting succeeds, the drive holds two copies of the partition-entry list, one near the front and one near the back, and each copy always contains exactly 128 fixed-size slots of 128 bytes with every slot beyond the partitions the caller asked for filled entirely with zero bytes, regardless of how many partitions were requested.✓·

DPM-READ-MYLBA-UNCHECKEDinitialize, initialize_or_formatEach header records which sector it lives in and where its partner copy lives, and the read path never checks either value against the sector it actually read the header from, so a header relocated or misattributed on the drive is accepted as if it belonged where it was found.✓·

DPM-INV-ENTRY-ARRAY-SHAPEinitialize, format, partition_info, num_partitions, initialize_or_formatThe on-disk list of partition entries always consists of exactly 128 entries, each occupying exactly 128 bytes, giving a fixed 16 kilobytes of entry data for both the main and the backup copy whatever the drive or layout.✓·

DPM-INV-GUID-V4-BITSformat, initialize_or_formatEvery identifier this component generates, for the drive as a whole and for each partition, carries the marker bits that declare it a randomly generated identifier of the standard kind — version 4 and variant 1 — so other tools recognise its format.✓·

What these times include. Each figure is the sum of the first proof attempt per property, as measured by the scorer around one whole toolchain invocation (/usr/bin/time -v cargo kani --harness <h> or cargo creusot <module>). So it is build + proof, not solver time: a sub-second proof still shows seconds because compilation is counted with it, and Kani re-invokes the toolchain per harness while Creusot's runs are largely incremental — which is most of why Kani's per-property figures sit well above Creusot's. A figure at or near the cap (--cap-seconds, escalating once to --cap-max) is a timeout, not solving.
What they exclude. The scorer also runs an anti-vacuity __mutant twin for each proved property and the full lever battery for each tool-boundary; those invocations are not counted here, so one property can cost 2–5 runs while only the first is timed. Total machine cost per tool is the stage wall-clock in verif/.run/<stage>.done, which is larger than the sum above. Peak RSS is the largest single timed run, not a total. Agent time to author the proofs is not measured anywhere on this page.
