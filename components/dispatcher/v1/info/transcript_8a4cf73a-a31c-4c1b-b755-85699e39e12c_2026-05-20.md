Yes. The pipeline overlaps them. Here's the concurrency at steady state:

```
chunk[i]   NVMe read complete ─→ issue cudaMemcpyAsync H2D on stream[i%2]
chunk[i-1] GPU H2D completes   ─→ sync stream[(i+1)%2] confirms this
chunk[i+1..i+N] NVMe reads in flight simultaneously (N = up to 16 primed)
```

In `pipelined_ssd_to_gpu_zero_copy`, after receiving an NVMe completion for chunk `i`:

1. **Immediately** issue `dma_copy_to_device_async` for that chunk (non-blocking — GPU DMA engine starts)
2. **Then** sync the *other* stream (waits for chunk `i-1`'s H2D to finish, not the current one)
3. **Then** submit the next NVMe read

So at any given moment:
- The GPU DMA engine is copying chunk `i` from memory-tier → GPU (async)
- The NVMe controller is writing chunks `i+1` through `i+N` into later memory-tier offsets (in parallel)
- The CPU is just dispatching commands and waiting on completions

This is the same overlap pattern as gpu-bb-vs-p2p. The SSD and GPU DMA engine run concurrently on different chunks — neither waits for the other except at chunk boundaries (you can't H2D a chunk until its NVMe read is done).
