Now I have a clear picture of the data path. Here's the answer:

**No — in the current implementation, promotion is sequential, not fully pipelined in parallel.**

When a lookup hits `LookupResult::BlockDevice` (i.e., the entry was evicted from the memory tier and only exists on SSD), the `promote_and_serve` method at `v1/src/lib.rs:186` calls `pipeline::pipelined_ssd_to_gpu`, which works like this (`v1/src/pipeline.rs:60-119`):

For each chunk, it does these steps **sequentially within a chunk**:
1. SSD read → ring buffer (wait for completion)
2. Copy ring buffer → memory-tier slot (`memcpy`)
3. DMA copy ring buffer → GPU destination

The "pipelining" is across chunks using a ring buffer (depth 4): while step 3 of chunk N is in flight, the ring slot for chunk N+4 is already free to accept a new SSD read. However, **within each chunk**, the SSD read must complete before the memory-tier copy and GPU DMA begin — those two are done back-to-back from the same ring buffer.

So the memory-tier is populated **as a side-effect of the same transfer that feeds the GPU**, not as an independent parallel operation. Each chunk lands in DRAM first, then gets copied to the GPU. The memory-tier doesn't receive data independently/asynchronously from the GPU path — they share the same sequential pipeline stage.
