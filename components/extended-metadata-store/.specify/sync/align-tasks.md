## Task: Align 001-extended-metadata-store/ALIGN-002

**Severity**: MAJOR

**Spec Requirement**: FR-05 (spec.md) — "`force_flush()` ensures all
mutations are durable on disk"; interface doc comment
(`components/interfaces/src/iextended_metadata_store.rs:44`) — "Flush all
pending writes to persistent storage. Returns when all data is durable."

**Current Code**: `IExtendedMetadataStore::force_flush()` is an
unconditional no-op in every build configuration (default, `testing`,
`spdk`) — `src/lib.rs:177-184`. It never calls `flush::flush_to_disk` or
`FlushManager::trigger_flush`. The only call site of `.force_flush()` in
the whole crate is a unit test asserting the no-op returns `Ok(())`. Every
persistence/SSD test that needs durability calls `flush::flush_to_disk()`
or `FlushManager::trigger_flush()` directly, bypassing the public trait
method entirely. A production caller that only knows the
`IExtendedMetadataStore` interface gets silent data loss on "flush".

**Required Change**: Wire `force_flush()` to actual persistence — e.g. have
it call into a held `FlushManager`/`flush_to_disk` when the
`testing`/`spdk` feature is enabled and the component has been initialized
with a `BlockDeviceClient` (via the FR-17 wiring API). If it is
architecturally intended that `force_flush()` is a hint-only method and
real durability must always go through a directly-held `FlushManager`
handle, that is also an acceptable resolution, but it must be an explicit,
deliberate design decision — not silently expose a durability-sounding API
that silently does nothing. Either way, this is a code change (`src/lib.rs`
and possibly `src/flush.rs` for the component-to-FlushManager wiring), not
a doc-only fix.
