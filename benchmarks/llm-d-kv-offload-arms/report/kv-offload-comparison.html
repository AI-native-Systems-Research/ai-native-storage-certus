llm-d · vLLM 0.30 · Qwen3-8B · 4 × NVIDIA A30 · long multi-turn chat

KV Offload Comparison

How quickly a long chat's next turn starts, when its history no longer fits in GPU memory: Certus against vLLM's own KV tiers, with prefill and decode on separate GPUs and with every GPU doing both.

Key results

  1. With prefill and decode split, Certus starts the next turn 2.7× faster than vLLM's documented tiered setup (0.64 s against 1.76 s median). Two things add up: Certus gets stored history from disk to the GPU faster, and it fetches each turn's answer back from the decode GPU so prefill does not recompute it.
  2. Fetching the answer back is worth 1.5×. With Certus's fetch turned off, the next turn takes 0.99 s; prefill recomputes each earlier answer.
  3. vLLM's P2P fetch does not survive the memory pressure. It pulls only from a peer's CPU memory, which the workload overflows, so it made no pulls and recomputed every prompt (2.88 s). Even modified to fetch from disk, so it pulls as often as Certus, it was 2.6× slower (1.64 s). Prefill keeps a fetched answer only in memory, which overflows, so each turn fetches every earlier answer again: four times the data Certus fetched. The source reads all of those blocks from disk before it replies, plus blocks prefill then loads from its own disk instead. Those extra reads come from our unsupported setup, about 200 ms of the gap, and changing the tier order does not remove them; the rest is how vLLM handles fetches.
  4. Without the split, the median is faster but the slow turns are far slower. Every GPU doing both jobs starts most turns in 0.28 s, but about 24 of 280 turns wait over 10 s behind other sessions' long answers, against 10 with the split. When the router moves a conversation to another GPU, Certus's fetch lets the new GPU take its history instead of recomputing it: over four runs each, turns taking 2–5 s fall from 28.5 per run to 7.

What is being measured

In a chat, each new turn's prompt is the whole conversation so far: the document, every earlier question, and every earlier answer. Before the model can write the first word of its reply it has to have the KV cache (the attention keys and values) for that entire prompt on the GPU. It can either load that KV from wherever it was stored after earlier turns, or recompute it. Time to first token (TTFT) is mostly that step.

The workload is built so the stored KV cannot all stay close: 40 conversations of 8 turns, each a 4,000-token document followed by questions with 2,000-token answers, about 110 GiB of KV in all, against 32 GiB of memory tiers across the four GPUs: 3.4 times too much. So most history has to come from SSD, from another GPU's store, or be recomputed, which is the case KV offload exists for.

P/D split
One GPU does every prompt pass (prefill); three do the generation (decode). Each turn's KV moves from prefill to decode over NIXL, GPU to GPU over RDMA. Each new turn's answer is produced on a decode GPU, but the next turn's prompt is processed on the prefill GPU, so that answer has to come back or be recomputed.
Aggregated
Each of the four GPUs does both. A conversation usually stays on one GPU, so its history is local, but the router may move it to another.
Fetch
Moving stored KV for a turn's history from the GPU that has it to the GPU that needs it, instead of recomputing it. The router names the source.
Certus
The KV store being evaluated: one instance per NUMA node, holding KV in DRAM and spilling to NVMe SSD, reached by vLLM through a connector. It fetches from a peer Certus over RDMA.
vLLM tiers
vLLM's built-in alternative: a CPU-memory tier on each GPU's server, optionally spilling to a filesystem, optionally sharing with peers (P2P).

Question 1

Does fetching the answer back help, in a P/D split?

Yes, by 1.5×. With fetch, prefill takes each earlier answer from the decode GPU's Certus over RDMA; without it, it recomputes them. Prefill loads 95% of the prompt from Certus instead of 79%, and recomputes 4.4 times less.

Median TTFT 0.64 s vs 0.99 s Difference -0.35 s (95% CI -0.39 to -0.28 s)P/D · NIXL + Certus, with fetch is 1.54× faster

The gap grows with the conversation: each later turn has more earlier answers to bring back.

Question 2

How does Certus compare with vLLM's own tiers?

Certus is 2.7× faster than vLLM's documented multi-tier setup, and 4.5× faster than llm-d's documented P2P setup, which fetches nothing under this load.

Against vLLM CPU + filesystem: two separate effects

Storage path alone. Neither side fetches, and both reuse exactly the same 79.5% of prompt KV, so only the path from storage to the GPU differs. 0.99 s against 1.76 s: Certus 1.78× faster (95% CI -0.87 to -0.63 s).
Plus fetch. Certus as deployed, against vLLM's documented setup. 0.64 s against 1.76 s: Certus 2.74× faster (95% CI -1.21 to -0.96 s).

The experimental configuration, vLLM's P2P made to fetch from disk too, is included for comparison; Question 3 covers it.

Against vLLM P2P

llm-d's P2P setup lets prefill pull an earlier answer from a decode GPU's CPU tier. Here the CPU tiers overflow, decode has evicted each answer before prefill asks, and the router named no source on any of 316 turns. With no disk tier under it, prefill recomputed every prompt.

Question 3

If vLLM's P2P could fetch from disk too, would it match Certus?

No. Made to fetch exactly as often as Certus, it is still 2.6× slower, about as slow as vLLM's tiers with no fetch at all.

To test this fairly we added vLLM's filesystem tier to its P2P setup and changed vLLM's KV-cache events so the router treats blocks on disk as fetchable, which is how it already sees Certus's SSD. vLLM accepts the combination but does not document it, so this is an experiment, not a supported configuration. It worked as intended: the router named a source on all 280 follow-up turns, the same as Certus, and prefill loaded 95.3% of the prompt instead of recomputing it.

Median TTFT 0.64 s vs 1.64 s Difference -1.00 s (95% CI -1.08 to -0.91 s)P/D · NIXL + Certus, with fetch is 2.55× faster
Why equal fetching does not give equal speed Not the data path: both read a block from disk into host memory on the source, send it over RDMA, and copy it into the GPU on the requester. We reran this configuration with vLLM's P2P logging turned up and timed every step of all 279 fetches. The rerun took the same time as the original (median 1.66 s), so the logging did not change the result. A fetch took a median of 738 ms. 558 ms of that was the source getting the blocks ready before it replied; the reply, the fetch request and the RDMA write together took 127 ms. Three things make that wait long. 1. vLLM fetches the same answers again and again. When prefill fetches a block, vLLM puts it only in prefill's CPU memory, not on its disk: prefill wrote just 26.3 GB to disk over the run, against 328.2 GB fetched. That memory overflows under this workload, so by the next turn the fetched answers are gone, and prefill fetches them again together with the newest one: 125 blocks on the second turn, 250 on the third, up to 875 on the eighth. Certus keeps a fetched block in prefill's own Certus, so each turn fetches only the newest answer: 35,160 blocks over 280 fetches, about 125 each, 82.6 GB in all against vLLM's 328.2 GB. 2. The source reads every block from disk before it replies. A conversation's next turn arrives about 324 s after its last answer. In that time each decode GPU stores 9.3–9.5 GB of new answers, more than its 8.56 GB memory tier holds, so in both systems the blocks a fetch wants have usually left memory for disk. vLLM's source found none of the 209,874 blocks it was asked for in memory. It reads them into its CPU memory, at about 3.2 GB/s, and replies only when all of them are in; the time grows with the number of blocks asked for, by about 0.78 ms per block. Those reads go through the same memory tier, another 22.9 GB per GPU between turns, which pushes out more of its own answers. Certus's source sends each block as soon as it has it, reads blocks that are on SSD into separate buffers rather than into its memory tier, and is asked for only the newest answer. 3. The source also reads blocks prefill does not take. Prefill asks its P2P tier and its own disk about the same blocks at once, a median of 753 per fetch. Its own disk supplies the older part of the conversation, so prefill fetches only the earlier answers, a median of 500. The source has already read all of them: 70,597 blocks (166.6 GB) over the run that were never fetched, the same amount prefill read from its own disk (166.8 GB). At 0.78 ms per block that is about 200 ms of each wait. Putting the disk tier first does not help. To test whether point 3 is only a matter of configuration, we reran with prefill's disk tier ahead of P2P. Nothing changed: prefill still asked about a median of 753 blocks per fetch, and the median turn took 1.62 s against 1.66 s (-0.04 s, 95% CI -0.24 to +0.13). vLLM's disk tier answers a lookup a scheduler step later, and an unanswered tier does not stop the lookup from moving on, so in the first step every block goes to both tiers whatever the order. When the blocks are in memory, the same fetch is fast. In a smaller run where the source still had the blocks in memory, it replied in a median of 4 ms and a whole fetch took 108 ms, mostly the RDMA write. So vLLM's P2P mechanism itself is not slow; what it has to read from disk, and how often, is. How much is our setup, and how much is vLLM? Point 3 comes from our unsupported setup, P2P and a filesystem tier on the same engine: about 200 ms of the 1.0 s gap, and no tier order removes it. Points 1 and 2 are how vLLM handles fetched blocks and peer requests, and they account for most of the rest, together with vLLM's slower path from disk to GPU (Question 2). In vLLM's documented P2P setup the source serves only from memory, which under this workload has already lost the blocks, so that setup fetched nothing.
Question 4

Is splitting prefill and decode worth it?

It depends on what matters. Without the split the typical turn starts 2.3× sooner; with it, slow turns are far rarer.

Median TTFT 0.28 s vs 0.64 s Difference -0.36 s (95% CI -0.41 to -0.32 s)Aggregated · Certus, with fetch is 2.29× faster

Each bar counts follow-up turns by how long they took to start. Aggregated serving has no prefill-to-decode hand-off, so most turns start in under half a second. But a GPU busy writing other sessions' 2,000-token answers makes a new turn wait: 24 turns waited over 10 s, against 10 with the split, where prefill has a GPU of its own. That wait is queueing in vLLM, not loading: its own counters show the same number of requests queued over 10 s.

What fetch adds when every GPU does both

About 30% of follow-up turns land on a different GPU from the conversation's previous turn, when the router balances load. Without fetch such a turn recomputes its whole history, typically 2–5 s; with fetch the new GPU takes the history from the old GPU's Certus. Copy rate is bytes loaded into the GPU divided by the time vLLM spent loading them, from vLLM's own counters. It is about 15–20 GB/s in every configuration that loads at all, so the final copy into the GPU is not what separates them. Two things do:

  • How much is recomputed. Recomputing costs GPU time at the start of every turn. The configurations that fetch recompute 24–35 GB of KV over the run; those that do not, 107–116 GB; vLLM's P2P setup under overflow, all 511 GB.
  • How fast the store behind the copy is. vLLM loads into the GPU only from its CPU tier, so a block on disk is first read into CPU memory before the copy can start; vLLM's filesystem tier read at about 3.6 GB/s per server here. Most of Certus's loads (about 416 GB of the 496 GB in the split configuration with fetch) came from its SSD, and its fetch moved 82 GB between servers over RDMA. For a fetch from a peer, Question 3 shows the wait for the peer to answer matters more than either.

How the comparison was kept fair

Hardware
Two servers, each with two NVIDIA A30 GPUs (24 GB) on separate NUMA nodes, eight NVMe drives and a RoCE network card.
Memory
7.97 GiB of memory tier per GPU in every configuration (Certus's 8 GiB less its transfer buffer, and the same cpu_bytes_to_use for vLLM), and the GPU KV cache fixed at 37,184 tokens on every pod.
Disk
The same eight NVMe drives per server: driven directly by Certus (SPDK), or given to vLLM as one RAID 0 + XFS array per NUMA node.
Placement
In every split configuration prefill runs on the same GPU and decode on the other three; the hand-off is NIXL over RDMA.
Routing
llm-d's router at a pinned release, with the same placement rules for every split configuration and for both aggregated ones. Where fetch is on, the same rule picks a source: the GPU whose store holds at least 1,024 more tokens of the prompt than the GPU doing the work.
Starting state
Every run starts from empty stores.
Answers stored
Every configuration stores the answers it generates, not only prompts. An answer is the next turn's prompt; vLLM's default of storing prompts only would make every configuration recompute it.
Software
vLLM 0.30.0 with the Certus connector in one image for every configuration. Certus built with CUDA 13.2, which lets it copy a block's 36 per-layer pieces to the GPU as one batched transfer.

Limits

  • One run per configuration, except the two aggregated ones, which ran four times each on the same build as the rest. Other confidence intervals are bootstrapped over the 280 turns of one run, not across runs.
  • The experimental vLLM P2P + filesystem configuration is not supported by vLLM or llm-d, and its routing change is our own patch. A version designed for fetching from disk could do better.
  • The two split Certus configurations were rerun on a Certus build that fixes a startup race, which could leave a server with fewer than its four drives. The reruns match the earlier runs within noise: 0.64 s against 0.63 s with fetch, 0.99 s against 0.95 s without. The aggregated runs were checked for all four drives before each run.
  • In the vLLM CPU + P2P configuration, one conversation ended after its fourth turn on an HTTP error from llm-d's routing sidecar, so it completed 315 of 320 turns.
  • One model, one GPU type, one workload shape. Shorter answers or longer histories would load prefill more and could change the throughput picture, which here is set by generating 2,000-token answers.
Measured on two servers with two NVIDIA A30 GPUs each, 30 October – 5 November 2026. Per-turn records, Prometheus scrapes and router decision logs for every run are kept with the run scripts.
